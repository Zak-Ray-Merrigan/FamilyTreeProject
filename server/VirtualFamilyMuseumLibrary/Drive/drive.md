# Overview
This resource is home for holding versioned templates and images. This drive consists of 2 containers:  
- templates: holds read-only view versioned snapshot of family tree content relative to a single inherited family name stored as PDFs.
- images: photos of individuals or family dynamics stored as JPGs.

# Key Constants
These are the key constants needed for my .NET 9 library to know in order to upload, download and delete templates and images:  
- Blob Service Endpoint (`FamilyDrive:BlobServiceEndpoint`)
- Container names (`FamilyDrive:ImageContainerName` and `FamilyDrive:TemplateContainerName`): images and templates

# Drive Extensions
`DriveExtensions` holds the conventions every other piece of this module is built on:
- `GetContainer(string blobName)`: reads the first `/`-delimited segment of a blob name (e.g. `templates/2026/August/14/file.pdf`) and resolves it to the matching `FamilyDriveContainers` value. Every blob name handed to the Repository must be prefixed with `images/` or `templates/` so it's clear upfront which container it belongs to; anything else throws `NotSupportedException`.
- `GetContentType(this FamilyContentTypes)`: converts a content-type enum value into its MIME string (e.g. `Application_PDF` -> `application/pdf`) for setting a blob's HTTP headers on upload.
- `GetContentType(this string)`: the reverse mapping, turning a blob's stored MIME type back into a `FamilyContentTypes` value when reading a blob back out. Throws `NotSupportedException` for anything not in the supported set.

# Models
- `FamilyDriveContainers`: enum identifying which container a blob lives in (`Images`, `Templates`).
- `FamilyContentTypes`: enum of the content types this drive supports (`Application_PDF`, `Image_JPEG`). Adding a new supported file type means adding a value here plus a mapping on both sides of `DriveExtensions.GetContentType`.
- `FamilyBlobResource`: the DTO returned by every Repository operation. Carries `BlobName` (the container-prefixed logical name), `BlobUrl` (the blob's Azure URI), `Content` (the blob's readable `Stream`), and `ContentType`.

These three describe a blob as Azure sees it — which container it's in, what its bytes mean, how to fetch/store it — regardless of what's inside. `HierarchicalCoordinate` and `TemplateLine`, also under `Drive/Models`, describe what's *inside* a `templates` blob once you have one; see Template Processing below.

- `FamilyDriveResult<T>` (`Drive/Models`): this drive's own extension of the project-wide `DomainResult<T>` — a shared type used across more than one category of this project, so it's described in the root [README](../../../README.md)'s Shared Models section rather than here. `FamilyDriveResult<T>` adds exactly one thing on top of it: a required `Status` of type `FamilyDriveResultStatuses`. This is the shape `FamilyDriveService` (see Family Drive Service below) hands back to a controller instead of a bare `FamilyBlobResource` — the controller reads `Status` to decide how to respond to React, and `Message` to know what to say, without necessarily needing a try/catch.
- `FamilyDriveResultStatuses`: `Success`, plus two predictable-failure statuses that exist specifically for `UploadImageAsync` — `UnsupportedContentType` and `IllegitimateContent`. Deliberately not exhaustive of every way an operation can fail: an *unpredictable* failure (one of the domain's own guarantees being violated, not the client's fault — see Family Drive Service) still throws an exception rather than getting its own status. `Status` only distinguishes outcomes a controller should expect and handle without exceptional control flow; genuine anomalies stay exceptions.

# Template Processing
This is a template-content concern, not a blob-storage concern: it's about modeling the PDF paragraphs found inside a blob stored in the `templates` container (content-type `application/pdf`), independent of how that blob was fetched or saved.

A template PDF renders one inherited family name's tree as a flat, depth-first-ordered list of paragraphs, each one either introducing a member (optionally alongside an in-law via a family dynamic — marriage, widowhood, divorce, co-parenting, etc.) or one of that member's children, e.g.:
```
1) Brian Bryan Kessler (Sep 1886 – Dec 1915) & Todd Zachary Vasterling (1911 – Present): 1948
1.1) Kit Dale Kessler (–)
1.2) Lisa Kaylynn Kessler (–) & Hallie Jordon Delacroix (21 Jan 1927 – Present): 11 May 1967
1.2.1) Kevin Nathaniel Kessler (21 Jan 1949 – Present) & August Hallie Aldous nee Bordt (9 Oct 1951 – Present): 22 May 1975
```
Sample trees illustrating this format live under `Resources/template_samples`.

- `HierarchicalCoordinate`: an immutable outline-numbering coordinate (`1)`, `1.1)`, `1.1.2)`, ...) — the vertex a `TemplateLine` occupies within the tree, in Graph Theory terms. Backed by an `int[]` of segments, one per generation of depth. `.ToString()` renders it exactly as it appears in a template (`1.1.2)`). `.Parent`/`.Child`/`.NextSibling` navigate the coordinate space itself to compute the next coordinate to assign while walking or building a tree — they don't touch any tree data. `IComparable`/operators order coordinates the same way the lines appear in the PDF: a coordinate always sorts before its own children, and siblings compare numerically per segment (`1.9)` before `1.10)`), not lexicographically. The all-empty coordinate is a virtual document root: `.Parent` and `.NextSibling` are `null`, `.ToString()` is `""`, and `.Child` yields `1)` — the first top-level entry.
- `TemplateLine`: one paragraph of a rendered template PDF — a member, positioned at a `HierarchicalCoordinate`, with an optional in-law and the date their family dynamic began. `Coordinate` and `MemberBirthName` are always required; `MemberBirthDate`/`MemberDeceasedDate` and `InLawBirthName`/`InLawBirthDate`/`InLawDeceasedDate`/`FamilyDynamicStartDate` are all optional. `.ToString()` renders a line back into the same text format the samples use — a missing birth date prints as `(–)`, a birth date with no deceased date prints as `(... – Present)`. The model assumes, without checking, that a deceased date is never set without a birth date (for both member and in-law), and that in-law dates and the family dynamic start date are never set without an in-law birth name — see the comment on the class. Enforcing those rules is domain/business logic and is deliberately left outside this model; where that validation should live is still an open decision.

Turning a template blob into a sequence of `TemplateLine`s happens in two steps, mirroring the two models above:

- `DriveExtensions.GetPdfPageLines(string[] initialLines)`: takes the raw lines iText extracts from a single PDF page (`PdfTextExtractor.GetTextFromPage`) and re-joins any that wrapped mid-paragraph back into one line per tree entry. A line only starts a new entry if it matches a hierarchical coordinate followed by whitespace and the start of a name (`^\d+(\.\d+)*\)\s+[A-Za-z]`); anything else is assumed to be the tail end of the previous line wrapping onto a new physical line and gets merged back on. That trailing-name requirement matters: without it, a wrapped date fragment like `1950)` or `2002):` looks coordinate-shaped too and gets misread as a new entry. Returns a `Queue<string>` so a consumer can drain normalized lines in the same top-to-bottom order they appeared on the page.
- `DriveExtensions.AsTemplateLine(this string line)`: parses one normalized line (as produced by `GetPdfPageLines`) into a `TemplateLine`, splitting on the format's own punctuation (`(`, `)`, the en dash, `&`, `:`) to recover the coordinate, member, optional in-law, and optional family dynamic date. Throws `InvalidCastException` if the line's shape doesn't fit one of the valid combinations — an empty line, a member alone, a member with an in-law, or a member with an in-law and a family dynamic date. A malformed line is treated as a bug in the source template, not user input to recover from gracefully: templates are PDFs, generated from a known format, so a line that doesn't fit is a developer-facing failure.

`TemplateReader` (`Drive/Domain`) is what actually drives this end to end. Given a blob name, `ReadTemplateAsync` fetches it via `IFamilyDriveRepository`, confirms its content type is `Application_PDF` — anything else throws `InvalidOperationException`, same as a blob that isn't found — and returns a lazy `IEnumerable<TemplateLine>` backed by a custom `IEnumerator<TemplateLine>`. That enumerator only ever holds one page's worth of normalized lines in memory at a time: `MoveNext()` drains the current page's queue one `TemplateLine` at a time, and once it's empty, fetches, extracts, and normalizes the next page before continuing — so a large multi-page template is never fully parsed up front, and pages are pulled from Azure Blob Storage lazily as the caller actually enumerates. Logging is split by intent: `Information` covers per-read lifecycle (opening a blob, and one summary line on close reporting how many lines/pages it produced), while per-page and per-line detail — including real member names and dates — is `Debug`, so it only reaches a log sink when someone has deliberately raised the level to investigate a specific read.

`TemplateReader` is resolved through Dependency Injection, not constructed directly. `DriveExtensions.AddFamilyDrive(this IHostApplicationBuilder builder)` registers both it and `IFamilyDriveRepository`/`FamilyDrive` into the host's service collection; call it once during startup, after configuration is wired up via `AddConstantStorePipeline`, and any of the four execution contexts — Console, API, Functions, or an NUnit test's own `Host.CreateApplicationBuilder()` — can resolve a ready-to-use `TemplateReader` through constructor injection. `FamilyDrive`'s `IConfiguration` dependency is resolved from the container itself rather than captured from the builder directly, which works uniformly across all four contexts because `IConfiguration` is registered automatically by any `IHostApplicationBuilder` (`HostApplicationBuilder`, `WebApplicationBuilder`, and the Azure Functions isolated-worker builder all guarantee this) before `AddFamilyDrive` ever runs.

# Template Writer
This is the reverse concern from Template Processing's read side: turning an already-assembled, in-order sequence of `TemplateLine`s — assembling that sequence from wherever the family's authoritative data actually lives is the caller's responsibility, not this layer's — into a rendered, versioned PDF blob.

- `DriveExtensions.WrapTemplateLine(string text)`: word-wraps one rendered `TemplateLine.ToString()` into the physical lines it will occupy on the page. It only ever answers "how does this text break into lines no wider than 75 characters" — it has no notion of a page, and never decides whether those lines fit on one. Tokens (`text.Split()`) are packed onto a line greedily, up to 75 characters, starting a new line when the next token would push it over. A single token 75 characters or longer throws `ArgumentException` instead of being hyphenated or truncated: a properly-spaced real name or date token never comes close to that length, so a token that long is treated as a sign of upstream data corruption (e.g. a missing space) worth failing loudly on, not a typography problem worth solving silently.
- `DriveExtensions.PackPages(IEnumerable<IList<string>> physicalLineGroups)`: the page-layout counterpart to `WrapTemplateLine` — each group (one `TemplateLine`'s wrapped output) gets placed into fixed 49-line pages, one group at a time, checked against the page's *exact* remaining capacity (`physicalLines.Count`, not an estimate) before any of that group's lines are written. This is deliberate: a `TemplateLine`'s physical lines must never be split across a page boundary. If a group doesn't fit in what's left of the current page, the *whole* group moves to a fresh page rather than spilling partway across two. A group that alone exceeds a full page's capacity throws `ArgumentException` — the page-level counterpart to `WrapTemplateLine`'s single-token guard, for the same reason: real template content never comes anywhere near 49 physical lines for one member/in-law/family-dynamic entry.
- `TemplateWriter` (`Drive/Domain`) drives both of the above end to end via `WriteLinesAsync(string inheritedFamilyName, IEnumerable<TemplateLine> templateContent)`:
  1. Wraps every `TemplateLine` (`WrapTemplateLine`) and packs the resulting groups into pages (`PackPages`). An empty `templateContent` throws `ArgumentException` rather than producing a blank PDF.
  2. Derives a date-partitioned blob name — `templates/{year}/{month}/{day}/{inheritedFamilyName}.pdf` — so a write is versioned by the day it happened. Writing the same family name again on the same day overwrites that day's version; writing on a different day produces a new one.
  3. Draws each page with iText's low-level `PdfCanvas` API (`BeginText`/`MoveText`/`ShowText`/`EndText` per line) rather than the higher-level `iText.Layout` API, deliberately: `Layout.Canvas`/`Paragraph` can still re-wrap a line to fit its assigned width if the 75-character budget doesn't correspond exactly to the font's physical glyph widths at the area it's given, which would silently reintroduce the unpredictable auto-wrapping `WrapTemplateLine`/`PackPages` exist to eliminate in the first place. Raw `ShowText` never wraps, under any circumstances, so whatever `WrapTemplateLine` decided is exactly what gets rendered. Pages are US Letter (`PageSize.LETTER`), 11pt Helvetica (a built-in PDF standard font, so there's no font file to ship, embed, or otherwise manage across environments), 50pt left margin, first line at y=750, 14pt line height — measured against Helvetica's actual ascent/descent and realistic line widths at 11pt to confirm real margin is left on every edge of a Letter page.
  4. Uploads the finished PDF via `IFamilyDriveRepository.SaveAsync`. One subtlety worth calling out because it's easy to silently regress: `PdfDocument.Close()` must run *before* the upload reads from the stream (an unclosed `PdfDocument` hasn't flushed its xref table/trailer yet, so the stream isn't a complete, valid PDF), but `PdfDocument.Close()` also closes its underlying stream by default — which would make that same stream unreadable for the upload that has to follow it. `writer.SetCloseStream(false)`, set once right after constructing the `PdfWriter` and before any page is drawn, is what keeps the stream open across that boundary so both things can be true: the PDF is fully finalized, and the stream handed to `SaveAsync` is still readable.
  5. Logging follows the same split as `TemplateReader`: one `Information` line at the start and one at the end of a write — never per-line or per-page, so ingestion cost scales with writes, not with template size — an `Error` logged at the exact point a failure is detected (an empty template, a failed upload) right before the corresponding exception, and `Debug` for per-line/per-page detail. `Error`, not `Warning`: per Microsoft's own `LogLevel` guidance, `Warning` is for something abnormal that doesn't stop execution, while `Error` is specifically for a failure that stops the current activity — which is exactly what's happening the instant before each of these throws. (`TemplateReader`'s two thrown-exception sites follow the same `Error` convention.) Neither `TemplateReader` nor `TemplateWriter` attaches the exception instance to that `LogError` call, though — they log a message and construct/throw the exception as a separate step. `FamilyDriveService` (see below), written later, tightened this: it constructs the exception first, logs it via the `LogError(exception, message, args)` overload, then throws that same instance, so a sink can capture the real stack trace rather than just a message string.

`TemplateWriter` is resolved through the same DI registration as `TemplateReader` — `DriveExtensions.AddFamilyDrive` registers both.

# The Bijection Between a Template PDF and the Polyglot Database
A Template PDF isn't just a rendering of a family's data — it's designed to be a complete, uniquely-identifiable, and (in principle) reversible stand-in for it. That's a bijection: a mapping that's both injective and surjective between an Inherited Family Name's state in the polyglot Neo4j/Cosmos DB store and its Template PDF.

- **Injection** — reverting the database information relative to a certain Inherited Family Name to a stable, versioned Template PDF. Distinct inputs never collapse onto the same output: a different family name always resolves to a different blob, and the same family name resolves to a different blob on a different day, because the blob name is literally keyed on both (`templates/{year}/{month}/{day}/{inheritedFamilyName}.pdf`, see Template Writer above). "Stable" means deterministic — the same underlying data, written again, produces the same rendered content — and "versioned" is what makes that determinism observable and safe: a write never silently overwrites a *different* day's snapshot, only ever that same day's.
- **Surjection** — selecting an Inherited Family Name, traversing the Neo4j graph, and assessing the Cosmos DB documents (person and family dynamic) per vertex, writing each as a `TemplateLine`, then writing every `TemplateLine` onto the PDF. For this to genuinely be onto, the traversal has to be exhaustive: every vertex reachable from that family name's root — which is exactly what `HierarchicalCoordinate` exists to address, positioning a `TemplateLine` at its vertex "in Graph Theory terms" (see Models above) — must produce a corresponding `TemplateLine` in the output. Nothing reachable in the graph is allowed to go unrepresented in the PDF.

Put together: every vertex the graph traversal reaches ends up as a line in the PDF (surjective), and no two distinct family/day snapshots are ever represented by the same PDF (injective) — so the PDF is a faithful, uniquely-addressable, complete stand-in for that slice of the polyglot database.

That said, the full chain described above has two halves, and only one of them is built and proven today:
- **`TemplateLine` sequence &harr; Template PDF** — this half is what `TemplateWriter`/`TemplateReader` actually implement, and it's the half that's empirically verified, not just asserted: `TemplateWriterTest`'s round-trip tests write a known `TemplateLine[]`, read the resulting PDF back via `TemplateReader.ReadTemplateAsync`, and assert the result is exactly the original sequence — including a case specifically constructed to span multiple pages, so the round trip is proven across a page boundary too, not just within one page.
- **Polyglot DB (Neo4j graph + Cosmos DB documents) &harr; `TemplateLine` sequence** — this is the half described by "Surjection" above (traverse the graph, assess Cosmos DB documents per vertex, write each as a `TemplateLine`). `TemplateWriter.WriteLinesAsync` accepts this sequence as an already-built `IEnumerable<TemplateLine>` parameter; it doesn't perform the traversal itself. The traversal and per-vertex Cosmos DB lookup is the target design for a not-yet-built layer (a Controller, in the originally described architecture) — until that exists, this half of the bijection is a design intent to build toward, not yet a property the code enforces or tests can verify.

# Repository
- `IFamilyDriveRepository`: the contract for the drive — `GetAsync`, `SaveAsync`, and `DeleteAsync`, each keyed by a container-prefixed blob name (see Drive Extensions) and each returning `null` when the target blob doesn't exist. Blob storage only — it has no awareness of `HierarchicalCoordinate` or `TemplateLine`; a template blob's `Content` stream is just bytes to it.
- `FamilyDrive`: the Azure Blob Storage implementation. Authenticates via `DefaultAzureCredential`, so whatever identity runs it — a developer signed in via `az login`, or the ACA-hosted API's managed identity — needs Storage Blob Data Owner/Contributor on this account. It reads its endpoint and container names from configuration (see Key Constants), then resolves the target `BlobClient` by routing on the blob name's prefix and stripping that prefix off before handing the remainder to the Azure SDK, since the SDK's container clients are already scoped to a single container.

# Family Drive Service
`FamilyDriveService` (`Drive/Domain`, registered the same way as `TemplateReader`/`TemplateWriter` — via `DriveExtensions.AddFamilyDrive`) is the surface a controller actually talks to for everything that isn't structured template-content processing: downloading a blob to serve back to React, removing one, and uploading a new image. Unlike `TemplateReader`/`TemplateWriter`, it never touches `TemplateLine`/`HierarchicalCoordinate` — it only ever deals in raw blobs (`FamilyBlobResource`) and the `FamilyDriveResult<T>`/`bool` shapes it hands back. It exposes six public methods across three verbs, two containers each: `DownloadImageAsync`/`DownloadTemplateAsync`, `RemoveImageAsync`/`RemoveTemplateAsync`, and `UploadImageAsync` alone — templates are only ever written by `TemplateWriter`, never uploaded by React, so there's no template-side upload.

**Download** — `DownloadImageAsync`/`DownloadTemplateAsync` both delegate to a shared private `DownloadAsync(blobName, expectedContentType, isLegitimate, legitimacyDescription)`, parameterized rather than duplicated per entity type after a bug fixed in one copy (a missing exception type in the PDF legitimacy check, below) turned up with no guarantee it'd be caught in the other:
1. Null `blobName` throws `ArgumentNullException` — `repository.GetAsync` eventually calls `DriveExtensions.GetContainer`, which assumes a non-null string, so an unguarded null would surface as a raw `NullReferenceException` instead.
2. `repository.GetAsync(blobName)` runs directly, with **no separate container check beforehand**. That's a deliberate simplification, not an oversight: `FamilyDrive.GetBlobClient` already calls `DriveExtensions.GetContainer` as its first step, so an unrecognized container prefix (e.g. `"documents/file.txt"`) throws `NotSupportedException` on its own, propagating unwrapped as the unexpected failure it is — a domain-level pre-check would only be re-deriving something the repository was always going to enforce. A *recognized-but-wrong* container (a `templates/...` blobName passed to `DownloadImageAsync`) doesn't need a separate check either, because container and content-type are 1:1 by construction in this system (`TemplateWriter` always saves `Application_PDF`, `UploadImageAsync` always saves `Image_JPEG`) — fetching from the wrong container always produces a content-type mismatch, which step 4 below already catches. `null` back from `GetAsync` throws `FileNotFoundException`: a blobName reaching this method is assumed to already be guaranteed to exist (e.g. it came from a Cosmos document's own reference to a prior successful upload), so its absence is a genuine data-integrity anomaly, not a routine "not found" a client typo'd their way into — same reasoning as the container check, just surfaced later.
3. Content-type mismatch (`EnsureContentType`, shared with Remove — see below) throws `InvalidOperationException`.
4. The fetched `resource.Content` is buffered into a `MemoryStream` and the original is disposed (`await using`) — the Azure download stream isn't guaranteed seekable, and the legitimacy check below consumes whatever it reads, so a seekable copy is needed both to validate it and to hand the controller back a stream still positioned at 0. Buffering also means the original repository stream — never returned to the caller once copied — gets a clear owner responsible for disposing it, rather than leaking it.
5. The buffered copy runs through `IsLegitimateJpeg`/`IsLegitimatePdf` (passed in as `isLegitimate`, a `Func<Stream, bool>`). A `false` result disposes the buffer (nothing will consume it) and throws `InvalidOperationException`.
6. On success: `Status = Success`, `Message` names the blob and its content-type, `Payload` is a `FamilyBlobResource` built from the buffered stream — giving the controller both the bytes and the `ContentType` it needs to set the right header when responding to React (an `<img>`/PDF-viewer response needs both; the domain is the only place that reliably knows the real content-type, so it's handed over rather than left for the controller to assume).

**Remove** — `RemoveImageAsync`/`RemoveTemplateAsync` delegate to a shared `RemoveAsync(blobName, expectedContentType)`, returning a plain `bool` rather than a `FamilyDriveResult<T>` — a controller only ever needs to know whether the blob is gone. It fetches via `repository.GetAsync` first rather than calling `repository.DeleteAsync` unconditionally, specifically so the content-type can be checked *before* committing to the delete: `FamilyDrive.DeleteAsync` deletes the moment it finds a blob and only returns metadata about what it deleted afterward, so there's no way to reject a wrong-content-type blob through that call alone — by the time it returns, the deletion already happened. `null` back from the fetch returns `false` — unlike Download, "nothing to remove" is a normal, expected outcome here (an idempotent double-delete, a race), not an unpredictable one, so it's logged at `Information` and returned rather than thrown. A content-type mismatch still throws `InvalidOperationException` (via the same `EnsureContentType` Download uses) *before* any deletion, and the tests for this specifically assert the blob is still retrievable afterward — proving the reject-before-delete ordering holds, not just that it's intended to.

**Upload** — `UploadImageAsync(Stream content, FamilyContentTypes contentType)` is the one place in this class where failure can be the *client's* fault rather than the domain's own guarantee being violated, and it's handled differently as a result:
1. Null `content` still throws `ArgumentNullException` — a caller passing no stream at all is a programming error, not a bad upload.
2. Wrong `contentType` (anything other than `Image_JPEG`) returns `FamilyDriveResult<FamilyBlobResource>` with `Status = UnsupportedContentType` and `Payload = null` — no exception, no stream read at all (the cheapest check runs first).
3. The stream is buffered (same reasoning as Download's step 4) and checked with `IsLegitimateJpeg`. A non-legitimate JPEG returns `Status = IllegitimateContent`, `Payload = null`, and disposes the buffer. Note `content` itself — the caller's own stream — is never disposed here, unlike `resource.Content` in Download/Remove: the domain didn't create it, so it doesn't own its lifecycle.
4. A random, time-ordered blob name is generated — `images/{Guid.CreateVersion7()}.jpg` (.NET 9's UUID-v7 API, chosen so blob names sort in upload order) — and uploaded via `repository.SaveAsync`. Unlike the two checks above, `SaveAsync` returning `null` *does* throw (`IOException`): that's a genuine infrastructure failure, the domain's own guarantee (an accepted upload gets saved) being violated, not a client mistake.
5. On success: `Status = Success`, `Payload` is the resulting `FamilyBlobResource` — its `BlobName` is what the controller stores against the Cosmos document (a Person or a `FamilyDynamic`, never both) it was uploading on behalf of.

**Shared validation, `IsLegitimateJpeg`/`IsLegitimatePdf`** — both are structural checks, not full decodes: they confirm the buffered content actually parses as a real file of the expected format, catching corruption or format-spoofing beyond a shallow magic-byte check, without paying for full pixel decoding or PDF text extraction on every call.
- `IsLegitimateJpeg` uses SkiaSharp's `SKCodec.Create`, which reports failure via an `out SKCodecResult` rather than throwing. SkiaSharp was chosen over SixLabors.ImageSharp specifically to avoid cost: ImageSharp 4.x nags for a paid license key above a certain scale (via the Six Labors Split License), while SkiaSharp is MIT-licensed with no such gate — and nothing here needs ImageSharp's broader manipulation/encoding feature set anyway, only format validation. One non-obvious behavior, found by testing rather than documentation: `SKCodec.Create(Stream, ...)` takes ownership of and disposes whatever stream it's given once the codec itself is disposed, which would silently close the buffered content out from under the caller (still needed afterward as `Payload.Content` on success). Wrapping the stream in `new SKManagedStream(content, disposeManagedStream: false)` before handing it to `SKCodec.Create` keeps ownership with the caller.
- `IsLegitimatePdf` opens the stream with iText's `PdfReader`/`PdfDocument` and checks it has at least one page. Malformed input doesn't reliably throw a single exception type: a stream with a real `%PDF` header followed by garbage throws `iText.Kernel.Exceptions.PdfException`, but a stream with *no* PDF header at all throws `iText.IO.Exceptions.IOException` — a different type, in a different iText namespace, that doesn't derive from `PdfException`. Both are caught. This was found the same way as the SkiaSharp behavior above: by constructing both malformed shapes and running them through the real check, not by trusting a single assumed catch clause.

**Shared plumbing** — `EnsureBlobNameNotNull` and `EnsureContentType` are extracted, not duplicated, across `DownloadAsync` and `RemoveAsync` (Upload has its own inline null/content-type checks, since its failure semantics — return a result, don't throw — differ enough that sharing wouldn't simplify anything). Both follow a plain "check the bad condition, throw, done" shape rather than "check the good condition, return early, then throw" — matching how every other guard clause in this class and in `TemplateReader`/`TemplateWriter` reads.
